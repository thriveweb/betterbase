# Building sites with this theme

Instructions for any coding agent working in this theme. Read the whole file before starting a build.

## Inputs

The brief gives: the Figma links, site name, dev URL, wp-cli admin user, site type (single page or multi-page, blog, WooCommerce), pages, menu, content types, forms, integrations, pages that aren't designed, and notes. Ask for anything missing before planning; don't guess it.

## Start of a build

1. Prove Figma access: read the design context of the first frame in the brief. If the connector is missing, unauthorised or the read fails, stop and say so. Never build from link previews, thumbnails, memory or guesses.
2. Set `Theme Name` in `style.css` to the site name. Keep the `betterbase_` prefixes, the `betterbase-theme` class, enqueue handles (`betterbase-theme`, `betterbase-fonts`, `betterbase-swiper`, `betterbase-blocks`), and `window.betterbaseBlocks`. There is no text domain; leave it.
3. Git: if the theme folder has no repo, `git init` and commit the starter as delivered. If it still carries the starter's remote, remove it. Client sites keep local history only: never add a remote, never push. Author: `Samantha Scott <20122623+sam-scott@users.noreply.github.com>`, no `Co-Authored-By` line. (The starter repo itself is the exception: it has a GitHub remote; push only when told.)
4. Read every frame in the brief (desktop and mobile, hover states, style guide) before planning.
5. Propose the block breakdown per page (existing block, existing blocks combined, or new block with a one-line reason), list every question in one batch, and wait for approval before building.
6. Where the design has no hover, focus or interaction frames, propose one convention in the question batch (for example: "badges keep their size, only the arrow rotates 45°; cards lift, images zoom") and apply it everywhere. Don't invent interactions per block, and never add a flip, tab or accordion behaviour the design doesn't show. The accordion block already expands on click; don't add a second pattern.
7. Put design problems in the question batch too: controls that will be hard to see (white outline arrows on a light image), the same layout drawn with different type sizes, text columns at different offsets on different pages. Propose the resolution; don't build the problem and fix it later.

## Reading the design

- The Figma connector is the only source of truth. Load its design-to-code guidance first, then use design context (exact values, copy, node ids) per frame, screenshots at a readable size for layout checks, and variable/style definitions for colours and type.
- The brief links frames rather than listing node ids: a Figma link copied with a frame selected includes its node id. Children are reachable from the frame's design context. If a structure call fails on a large page, drill in from the frame link instead of falling back to screenshots.
- Fonts come from the design's text styles. Google Fonts: set the URL in `betterbase_fonts_url()` (`functions/enqueue.php`) and `--font-primary` in both `assets/css/theme.css` and `assets/css/wysiwyg.css`. `betterbase_enqueue_fonts()` and the `mce_css` filter already load that URL on the front end, in the block editor, and in the TinyMCE iframe. Anything else (Adobe Fonts, commercial): ask for the kit ID or files and keep the current stack until they arrive. Don't substitute silently.
- Colours come from the variables/styles where defined, otherwise the most-used values. Add them to `betterbase_colors()` in `functions/colors.php`. A colour used as a section background needs `'background' => true`. A dark section needs `'dark' => true` so `betterbase_get_text_color()` adds `text-color-white`. Set `'tinymce' => false` to keep a colour out of the editor colour map.
- Images and SVGs: the design context hands out asset URLs that work with `wp media import <url> --user=<admin>` (SVG uploads need a user with `unfiltered_html`; the theme only allows the SVG mime type for those users). Give every image alt text.
- Missing states (no mobile frame, no hover, no blog design): say so and follow the theme's defaults.
- Component variants named "default" and "active" (or similar) are usually different types, not rest and hover states. Map every variant onto the button clone options (see Fields) and the block settings before proposing a new style.
- Gradients and overlays: take the stops and their positions from the design context, not an approximation. A gradient that stops at 48% is not one that runs to 100%. The starter overlay is `has-overlay`: a flat 30% black on `.background-image` / `.background-video`, not a gradient.
- As soon as the connector works, save a full-frame render of every frame (1000px strips are enough) and the design-context values you'll need into the session scratchpad. Connector access can lapse mid-build; the saved renders let the fidelity sweep finish without guessing.

## Stack

- ACF blocks only. No core Gutenberg blocks, no page builders, no new plugins without asking. The one core block on the allowlist is `core/shortcode`, so a Gravity Form can be embedded. Don't add other core blocks.
- Reuse existing blocks and block settings first, then combinations of them. A new block is justified only when the layout can't be built from existing blocks without hacks, or it's a repeating structure (repeater or CPT-driven).
- Inserter order is `betterbase_blocks_config()['allowed']['default']` in `functions/acf-blocks.php`. A new block goes in that list after `acf/block-page-banner`; a block that isn't listed registers but doesn't appear in the inserter. Posts use the shorter `allowed.post` list. Keep the `Block - …` sections in `assets/css/theme.css` in allowlist order.
- Starter blocks live in `blocks/block-<slug>/`. Copy `blocks/block-TEMPLATE/` for a new block: rename the folder and the PHP file to `block-<slug>.php`, and set the `block.json` name to `acf/block-<slug>`. `betterbase_block_type_metadata()` rewrites `renderTemplate` to that PHP file.
- Multicolumn is the column layout: 1 to 6 columns of WYSIWYG and buttons, count and alignment from the inspector. A row of text columns in the design is Multicolumn, not a new block.
- Contact reads phone, email, address, and socials from Global Options and shows them by its checkbox set, next to a Gravity Form chosen by ID. Contact details are never typed into a block.
- `post` is for blog posts only. Anything else is a CPT in `functions/post-types.php`, registered from `betterbase_register_custom_post_types()`. Follow testimonial when the entries are only picked by a block (not public, `supports` title, fields on the post in a `Single – …` group). Follow service when the entries need their own archive and single (`has_archive`, editor, a taxonomy if the design has categories).
- Site-wide content (contact details, socials, header button, policy links, search, breadcrumbs, notice) lives on the Global Options page. Add fields to the `Global – Options` group rather than hard-coding. Read them with `get_field('…', 'options')`.
- Header and footer are templates (`header.php`, `footer.php`, the `Site Header` and `Site Footer` sections in `assets/css/theme.css`), not blocks. Menus are the `header` and `footer` locations. The logo is `assets/img/logo-betterbase.svg`, included from the header, the footer, and the login screen. Replace that file for the client logo.
- Third-party integrations (Instagram, maps, embeds): stub the block with a placeholder and say what's needed (plugin, API key). The Instagram block is the pattern: it prints a placeholder and reads the Instagram URL from Global Options. Don't guess or install.
- Gravity Forms is the forms plugin. The contact block stores a form ID. `betterbase_gf_force_shortcode_atts()` forces ajax and hides the form title and description. Style forms in the existing `Global Forms` and `Gravity Forms` sections. Don't install a second forms plugin.
- Other plugins own their output. Where a plugin renders a layout (an Instagram feed, a map), the theme sets the container width and typography only. Don't restyle or reflow that markup; the client configures the plugin. WooCommerce is the exception already in the theme: `functions/woocommerce.php`, `woocommerce/`, `assets/css/woocommerce.css`, and `assets/js/woocommerce.js` load only when WooCommerce is active. Use those for a shop brief. Don't add shop templates anywhere else.
- Blog: a new post opens as Post Header, WYSIWYG, Post Footer, and `single.php` only prints `the_content()`, so the single layout is those blocks. The archive is `index.php` (also used by `category.php`): the posts page's own content, then category links, then a `grid-col-3` of `parts/entry-post.php` with `betterbase_get_pagination()`. It is a template, not a block.
- Leave the starter's defaults unless the brief asks: comments stay off, search excludes the `post` type, AOS and the Gravity Forms submit-button filter stay commented out, the `thrivex.io` noindex check in `header.php`, the login logo, the Thrive credit in the admin footer and console, and the "Site by Thrive" line in the footer all stay.

## Where things go

- Block: `blocks/block-<slug>/block.json` + `block-<slug>.php`. ACF group in `acf-json/` with unique keys, location `acf/block-<slug>`, title `Block – <Name>` (en dash, as the existing groups). A `Block - <Name>` section in `assets/css/theme.css` in the same order as the allowlist. `style.css` is the reset and the theme header; don't put block CSS there.
- Block settings (background, container, padding) are not written into each `block.json`. `betterbase_block_type_metadata()` injects them from `betterbase_blocks_config()['defaults']`, overridden by a `betterbase.settings` object in that block's `block.json` (see Logo Slider and Hero Banner). Shared inspector controls live in `assets/js/blocks.js` and read `window.betterbaseBlocks`. Content stays in ACF. The multicolumn column count and alignment are the pattern for a per-block control that isn't content: an attribute added in `betterbase_block_type_metadata()`, and a panel in `blocks.js`. Don't put WYSIWYG, images, or repeaters in `blocks.js`.
- A block PHP file starts with `betterbase_block_preview($block)` and `extract(betterbase_block_settings($block))`, then the `betterbase-theme` wrapper, the setting classes and styles, `container-{$container}`, and `wysiwyg-content` plus `betterbase_get_text_color($background_color)`. A block with a title puts it in `.inner-block-head` (`container-sm`, centred, `<h3 class="h2">`) and the rest in `.inner-block-main`, as Testimonials and Post Feed do. Hero and Page Banner own the page's `h1`. Empty editor state: `betterbase_block_empty()`. Buttons: `include` `parts/group-button.php` (it expects `$add_button` and `$button_alignment`).
- Cards and repeated fragments are includes in `parts/` (`entry-post`, `entry-testimonial`, `entry-product`, `entry-search`, `social-media`, `social-share`). Each expects an ID variable set by the caller (`$post_ID`, `$testimonial_ID`). The `Entry - Default` CSS styles any `entry-*` class with `.inner-entry-content`. A new card goes there with the same naming.
- Reuse the layout utilities in `theme.css` before writing new CSS: `flex-layout` with `flex-align-*` / `flex-justify-*` / `flex-gap`, `grid-col-1` to `grid-col-6`, `padding-sm` / `md` / `lg` (and `-top` / `-bot`), `text-align-*`, `text-size-*`, `image-square` / `image-portrait` / `image-landscape`, `is-desktop-only` / `is-mobile-only`.
- Behaviour already wired in `theme.js`: popups (`.trigger-popup[data-popup-id]` moved into `.site-popups`), read more (`.has-read-more` with `.toggle-read-more`), click-to-play video (`.video-wrapper.is-paused`), accordions, the responsive menu, and the search toggle. Reuse those hooks rather than re-implementing them.
- Colours: `betterbase_colors()` only. `betterbase_color_css()` prints them as `--{slug}` on `:root`. Fonts: `--font-primary` in `assets/css/theme.css` and `assets/css/wysiwyg.css`, URL in `betterbase_fonts_url()`.
- Type scale is set on `h1`–`h6` and `p` in the Typography section of `assets/css/theme.css`, and mirrored in `assets/css/wysiwyg.css`. Override per block only where the design differs. Extra sizes that aren't a heading use a utility in the Content Styling section (the starter has `text-size-large` at 20px and `text-size-small` / `text-size-sub` at 12px). Body copy is 16px. Snap new sizes to the 4px grid and put the same value in both sheets.
- Containers, kept in sync in three places (`--container-*` in `theme.css`, the allowlist in `betterbase_block_settings()`, and `containerOptions` in `blocks.js`):
  - `xs` 624px · `sm` 832px · `md` 1044px · `lg` 1256px · `xl` full bleed
  Default is `lg`. Side gutter is `calc(100% - 60px)`, and `calc(100% - 32px)` at 782px and below. `xl` is width 100%. Add another size only after it is approved, and add it in all three places.
- Media queries already in `assets/css/theme.css` and `assets/css/woocommerce.css` are `max-width: 1200px`, `max-width: 782px`, and `max-width: 640px`, plus the header pair `min-width: 992px` / `max-width: 991px`. WooCommerce also uses `min-width: 783px` as the pair of 782. Swiper breakpoints in `theme.js` and `blocks.js` are 640, 782, and 1200. New CSS and slider breakpoints use this set. `grid-col-2` stacks at 782. `grid-col-3` and `grid-col-4` go to two columns at 782 and one at 640. Don't switch the theme to container queries. There is no JS header breakpoint. If the header has to stack at a different width, change the 991 and 992 queries in `theme.css` together.
- Icons and other inline SVGs live in `assets/img/` and are printed with `betterbase_include_asset()` in `functions/helpers.php`. A filename is prefixed with `/assets/img/`; a path that already contains `/assets/img/` is used as given. The file is included only when it exists. The login logo is the same folder, referenced by URL in `betterbase_login_logo()`.
- Sliders use Swiper 11 from the CDN in `functions/enqueue.php`. A new slider block is added to the list in `betterbase_needs_swiper()`, initialised under `Init Swiper` in `assets/js/theme.js`, and again in `assets/js/blocks.js` with autoplay off. Don't set `viewScript` or `viewStyle` in `block.json`. In the editor, `theme.css` sets `pointer-events: none` on `.swiper` and links inside `.wp-block .betterbase-theme`, and previews re-init on `acf.render_block_preview`. New sliders follow that; don't add a second lock.
- Every new block folder gets a `preview.jpg` before the report: the block rendered from the live site at design width, scaled to 1000px wide. `betterbase_block_preview()` only shows it when the file exists, and `betterbase_block_type_metadata()` only sets `example` when it exists. Regenerate it when that block's design changes. The starter blocks don't all have one; don't backfill them unless the block's design changed.
- A template that repeats a block's layout by hand (the post archive header, the 404) offers the same options as the block when that block gains one. The starter overlay is `has-overlay` only. Don't add an effect or texture system unless the brief asks.

## Fields

- On a new block, one content WYSIWYG holds the heading and copy (the editor picks the level). Reuse wins over that rule: Hero, Page Banner, Gallery, Video, Contact, Post Feed, Testimonials, and Accordion already have a Title field. Use it when that block is the right layout. Don't add a second heading field to them.
- A section heading that isn't part of a reused block is a WYSIWYG block above the content, not a new field. Gallery, video, and the list-style blocks carry their own content. A heading that shares a row with controls (the testimonial and logo sliders) stays a field on that block, rendered in `.inner-block-head`.
- Choice labels short, no brackets. A pair of choices sits at 50% width, as Colour and Style do on the button clone. A single choice is full width. Add an instruction when the effect isn't obvious from the label (the post feed and testimonial pickers say to leave them blank for the latest items).
- Buttons are the `Clone – Button Group` (`group_661491f489c42`), cloned seamless with `prefix_name` 0. Options on that clone are the only button options: colour `default`, `white`, `blue`; style `filled`, `outlined`; alignment `start`, `center`, `end`; plus the link field. The clone group stays inactive so it doesn't appear on its own. Don't copy its fields, don't add a colour or style, and don't put site-specific hints on it. A hint that only applies in one place goes on the Global Options tab that owns the feature.
- Block-only content is a block field. A value goes on the post only when something other than that one block reads it: the testimonial rating, quote, and byline live on the testimonial (`Single – Testimonial`) because every testimonial card reads them. A block with no fields of its own (Post Header, Post Footer, Separator, Instagram) is on the shared `Block – Basic (No Editable Fields)` message group. A new field-less block joins that group, and the message says where its content comes from.
- Build for the general case, not the instances drawn. A list designed with four items has no fixed count. The design's columns and lists become the default settings, not a hard limit. Ask if a count should be locked.
- Image and gallery fields: set `"preview_size": "thumbnail"`. `betterbase_acf_image_preview_thumbnail()` forces it anyway.
- Padding top and bottom are the RangeControls in `assets/js/blocks.js`: min 0, max 300, step 10. Defaults are 80 and 80. Any value in `betterbase.settings` or written by a content script has to be one of those steps (0, 10, 20 … 300), so the editor can still select it. A design padding off that step is rounded to the nearest step and logged. Don't change the step or the max to fit one screen. At `max-width: 782px`, `.block-setting-padding` divides the stored value by 1.5.
- Content is built by script, not by hand: `wp eval-file` with `parse_blocks` / `serialize_blocks` and `wp_slash`. ACF block data is key-nested (`name` plus `_name => field_key`). A seamless button clone stores `add_button` and `button_alignment` under the clone's own keys, with no name prefix, at each level the clone appears (including inside a repeater). Keep the script in the scratchpad so content can be rebuilt.
- Once the site has been shown to anyone, never rebuild a page from the script: their edits would be lost. Change blocks in place with a script that parses the page, edits the block, and serialises it back. Export the database before any migration that rewrites content or moves fields.

## Design fidelity

- Faithful to the design, not gospel. Round to multiples of 4, prefer 8: 31 → 32, 26 → 24 or stays. No odd pixels for spacing, gaps, or font sizes. Unitless line-height to one decimal. The starter body line-height is 1.5; headings are 1.2.
- A section whose behaviour isn't clear from the static design (scrollers, tabs, counters): ask before building.
- Motion: the theme's `--transition` (`0.3s ease`) and the existing hover styles. Only add motion the design shows or the brief asks for. `prefers-reduced-motion` is already handled in `theme.css` and in the logo slider. Don't uncomment AOS unless the brief asks for scroll animation.
- Keep the theme's accessibility baseline: `main#site-main`, heading order, `aria-expanded` / `aria-hidden` on the menu and accordion, `:focus-visible` (4px solid `--blue`), AA contrast. If a design colour pairing fails AA, keep the design and flag it; don't change it silently.
- Dark sections get `text-color-white` from `betterbase_get_text_color()`, or hardcoded on the banners. The rule forces white on descendants and exempts `.button`, `button`, any class containing `text-`, an inline `color`, and `.gform_validation_errors`. Anything new with its own colour inside a dark section (badges, slider arrows, chips) needs a class containing `text-` so it stays exempt, and a check on a dark background.
- Cards, borders, and icon tiles must work on every background setting. The starter uses `rgb(from var(--token) r g b / n%)` and `currentColor`, not a dark-theme class. Follow that.
- Every feed, archive, filtered view, and search needs an empty state with a way back. Search already has one (`.search-empty` plus the search form). The post archive says "No posts found." Match that tone.
- Log every deviation from the design (what and why) for the final report.

## Code style

- Match the theme. Section banners:

```
/*-----------------------------------------------------------------------
    Section name
-----------------------------------------------------------------------*/
```

  Short `/* Label */` comments only. Reasoning goes in commit messages, not comments.
- Prefixed snake_case functions, one concern per file under `functions/`. PHP templating is `if () { ?>` … `<?php else: … endif; ?>`.
- jQuery in `assets/js/theme.js` under the matching section banner, and in `assets/js/woocommerce.js`. The block-settings panel at the top of `blocks.js` is `wp.element`, not jQuery. The Swiper inits below it are jQuery. Don't rewrite either.
- Never edit plugins, core, or `wp-config.php`.
- Spelling: `color` in identifiers, filenames, CSS, and JSON keys (`betterbase_colors`, `settings_background_color`, `text-color-white`). `colour` in prose: labels, instructions, comments, docs, commit messages. Editor labels already say "Background Colour" and "Centre".
- Class names must not collide with wp-admin's stylesheet, which loads inside the editor canvas: no bare `.card`, `.notice`, `.wrap`, `.hidden`, `.title`, or `.description` on theme markup. Prefix them with the block (`block-cards-item`). Utilities are scoped under `.betterbase-theme`.

## Build and verify

- Build real content in WP: pages, the menu assigned to the `header` location (and `footer` when the design has one), the front page, Global Options, forms. The site must be reviewable at the dev URL; no mock HTML.
- Seed enough content to exercise every behaviour: one more item than a slider shows at once, one more than an archive's page size, a testimonial quote long enough to show "Read more" (the card clamps past 40 words). Sliders with no arrows and archives with no pagination can't be reviewed.
- Use wp-cli for admin tasks. Don't attempt to log in to wp-admin (Solid Security locks out failed logins); use the logged-in browser tab if one is provided. If Password Protected is active, ask for the password before front-end checks.
- Check every page in the browser at desktop and 420px. Console clean, no PHP warnings, axe clean. Test the fresh state too (no menu assigned, empty fields).
- Editor check: the canvas must match the front end, not merely render. `assets/css/theme.css` is what the editor canvas loads. For every block on every page, compare computed styles between the editor canvas and the front end at the same width (colour, background, font, spacing, borders, display) and fix every difference. Rendering without errors is not the bar. Forms render for real in the editor, never as a placeholder. Every block loads without marking the post as changed.
- Fidelity sweep before reporting: lay the saved design renders beside full-page captures of the site at the design width, section by section, and measure section tops against the design's section map. Fix what differs; log what is kept.
- Responsive audit before reporting: every page at 375, 420, 640, 782, 992, 1200, 1280, 1440, and 1512. Nothing overflows, no clipped text, tap targets at least 32px. Grids stack on the viewport breakpoints above, not container queries. Set the header's stack point from the measured menu width by changing the 991 / 992 pair.
- Menu check: add a temporary submenu (two children, one with a long label) and check the header on desktop and the tray on mobile, even when the design has no submenu. Remove it afterwards. Submenus use `BetterBase_Submenu_Wrap`.
- Variants check before reporting: build a private page with every block in the settings the design doesn't use (each background: none, light grey, blue, black; each container; the multicolumn counts; no heading, no image, one item, ten items, long words). Fix what breaks, delete the page, note it in the report.
- Finishing list, done before the report: favicon and site icon from the logo mark (transparent, no white plate) with a `theme-color` meta; a branded 404 with quick links (the starter 404 is generic); the header menu items relabelled to the design; placeholder media (portraits, brochures, posters, feed posts) listed for replacement.
- Temporary content made for testing or captures (posts, pages, uploads, terms, menu items) is deleted when done and never left in the client's library. A setting changed for review (posts per page, a test item) is restored and its restoration confirmed in the report.
- Commit to main as work lands, one concern per commit, reasoning in the message. Never push.
- Finish with a report: blocks reused and created per page, CPTs, fields to fill in, things blocked (font licences, API keys, notification emails), deviations from the design, anything not built.

## After the report

- Keep the migration scripts. A field that moves, a block that splits, or a layout that becomes a setting is migrated by script for every existing post, never by re-entering content.
